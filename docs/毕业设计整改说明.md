# 毕业设计整改说明

## 1. 项目当前定位

当前仓库已经具备一个基础的课程 RAG 问答系统雏形：

- 后端使用 `FastAPI + LangChain + FAISS`
- 前端使用 `React + Vite`
- 已经具备课程 PDF 文档导入、向量库构建、问答接口、基础聊天页面

但从毕业设计要求来看，它现在更接近“最小可运行 Demo”，还没有达到“可交付、可复现、可答辩、可展示系统完整性”的标准。

你的任务书题目是：

`Design and Implementation of a RAG-based Q&A Assistant for University Courses`

根据任务书已提取出的要求，至少应覆盖以下 3 类成果：

1. 课程知识库构建与向量化检索
2. 问答生成与优化，并实现答案可追溯
3. 系统实现与评价，形成轻量化 Web 应用和实验分析结果

当前项目只完成了其中一部分，因此还需要进一步整改和补全。

## 3. 当前存在的核心问题

## 3.1 后端启动依赖在线模型，系统不可稳定复现

问题位置：

- [backend/main.py](/D:/hebut_rag/backend/main.py:15)
- [backend/embeddings.py](/D:/hebut_rag/backend/embeddings.py:1)

当前 `backend/main.py` 在模块导入时就执行 `qa_chain = build_chain()`，而 `build_chain()` 会进一步调用嵌入模型初始化。现在嵌入模型写死为：

`sentence-transformers/all-MiniLM-L6-v2`

这会在本地没有缓存时尝试联网拉取模型。一旦网络不可用、Hugging Face 无法访问、或者答辩机器环境不同，后端就可能直接启动失败。

这类问题对毕业设计影响很大，因为老师通常会关注：

- 项目能否稳定演示
- 是否可在指定环境复现
- 是否存在对外部网络的强依赖

### 必须补的内容

1. 将嵌入模型改为“本地可配置路径”或“已缓存模型目录”
2. 后端启动时增加异常处理，避免一导入就崩
3. 区分“系统启动”和“模型初始化”阶段
4. 在文档中写清楚模型准备方式、运行环境和依赖项

### 建议整改方案

1. 用环境变量管理模型路径，例如 `EMBEDDING_MODEL`
2. 将 `qa_chain = build_chain()` 改为懒加载或应用启动时初始化
3. 当向量库或模型缺失时，返回明确报错信息
4. 在 `README` 中增加“离线运行说明”

## 3.2 未实现任务书要求的“答案可追溯”

问题位置：

- [backend/rag_chain.py](/D:/hebut_rag/backend/rag_chain.py:20)
- [backend/main.py](/D:/hebut_rag/backend/main.py:21)

任务书中明确要求：

`implement an answer traceability function`

但当前接口只返回：

```json
{
  "answer": "..."
}
```

系统没有返回任何来源信息，例如：

- 命中的文档名
- 来源页码
- 参考片段
- 检索得分

前端也没有显示“参考资料”或“引用来源”区域。因此从毕业设计角度看，这一项目前属于未完成状态。

### 必须补的内容

1. 后端返回来源文档列表
2. 给每条答案附带文档名和片段
3. 如果 PDF 可提取页码，要返回页码
4. 前端展示“本答案参考了哪些资料”

### 建议整改方案

1. 将 RAG 链改成支持返回 `source_documents`
2. API 返回结构改成：

```json
{
  "answer": "...",
  "sources": [
    {
      "source": "xxx.pdf",
      "page": 12,
      "content": "..."
    }
  ]
}
```

3. 前端在机器人回复下方显示引用卡片
4. 论文中增加“答案可追溯设计”小节

## 3.3 知识库构建流程还只是脚本，不像正式系统模块

问题位置：

- [backend/build_vector_db.py](/D:/hebut_rag/backend/build_vector_db.py:1)

当前脚本存在这些问题：

- 代码在文件顶层直接执行
- 路径写死为 `source` 和 `vector_store`
- 没有命令行参数
- 没有日志输出和统计信息
- 没有失败处理
- 没有区分不同课程知识库

这说明目前知识库构建只适合你自己在本机跑一次，不适合作为“课程知识库构建模块”在答辩中展示。

### 必须补的内容

1. 将构建逻辑封装成函数
2. 支持命令行参数传入源目录和输出目录
3. 打印文档数、分块数、向量库保存位置
4. 对错误文档做异常处理

### 建议整改方案

1. 支持命令行方式运行：

```bash
python -m backend.build_vector_db --source source --output vector_store
```

2. 为不同课程预留目录结构，例如：

```text
source/
  data_structures/
  compiler/
vector_store/
  data_structures/
  compiler/
```

3. 在论文中明确说明：
- 数据来源
- 文档类型
- 分块策略
- 向量模型
- 检索方式

## 3.5 缺少“系统评价”与“实验结果”

这是当前最容易被忽视、但对毕业设计最重要的一项。

任务书里不只是要求你把系统做出来，还要求“System implementation and evaluation”。也就是说，最后答辩时不能只展示页面，而要说明：

- 系统是否有效
- 比普通问答方式好在哪里
- 回答是否准确
- 检索是否有帮助

当前仓库里没有看到以下内容：

- 测试集
- 评价样例
- 问答准确率统计
- 有无检索的对比实验
- 不同参数的效果比较
- 错误案例分析

如果这些内容没有，论文会显得“工程演示有了，但研究性和分析性不足”。

### 必须补的内容

1. 制作一批课程问答测试样例
2. 记录系统回答结果
3. 评估回答质量
4. 形成实验表格和分析结论

### 最低可行实验方案

建议至少做 20 到 30 个问题，覆盖：

- 概念定义类问题
- 原理说明类问题
- 比较分析类问题
- 课件细节定位类问题
- 易混淆知识点问题

然后做 3 组对比：

1. 不使用检索，直接问大模型
2. 使用当前 RAG 系统
3. 使用 RAG + 优化 Prompt 或更优检索策略

评价维度可用：

- 准确性
- 完整性
- 可解释性
- 是否引用到正确资料
